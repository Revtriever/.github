# Frontend Architecture — revtriever-fe

React 19 + TypeScript strict, Vite 8, TanStack Router (file-based, type-safe), TanStack Query,
Tailwind v4, Radix primitives. Path alias: `@/` = `src/`.

## Folder structure

```
src/
├── main.tsx                # router + provider stack; the only place that creates the router
├── routeTree.gen.ts        # generated by the TanStack Router Vite plugin (committed, never edited)
├── index.css               # Tailwind v4 entry: @theme tokens, .dark overrides, .surface-card, .numeric
├── routes/                 # file-based route tree — thin: wires a page, a guard, a search schema
│   └── -specs/             # route-level specs; the `-` prefix keeps them out of the route tree
├── app/                    # application shell and cross-feature concerns
│   ├── providers/          # QueryProvider, SessionProvider, ThemeProvider, ToastProvider, AnalyticsProvider
│   ├── layouts/            # AppShell, PageHeader, SessionSplash, UserMenu
│   └── copilot|plan|setup|dashboard|audit|dunning/   # shell-level UI that composes several features
├── features/<feature>/     # one per API bounded context (auth, billing, dunning, gateways, ...)
│   ├── api/                # query/mutation hooks + key factory — the ONLY place that calls the API client
│   ├── components/         # components that know this domain
│   ├── pages/              # route-level components (what a route file renders)
│   ├── schemas/            # zod schemas (+ mappers) for this feature's forms
│   ├── lib/ content/       # optional: pure helpers / user-facing copy for the feature
│   └── types.ts            # feature types derived from the generated API types
└── shared/
    ├── ui/                 # design system primitives (Button, Field, Modal, Alert, Money, EmptyState, ...)
    ├── lib/                # api client, formatters, analytics, realtime, small hooks, cn()
    ├── config/             # typed env (zod), app-target, roles
    └── audit|templates/    # domain-neutral pieces reused by several features
test/                       # setup.ts, render.tsx, router.tsx, msw/, fixtures/ (see the testing skill)
```

Features that don't need a layer simply don't have the folder (`copilot` is only `api/`; `audit`
has `api/` and `pages/`). Create `components/`/`pages/`/`schemas/` when the first file needs it.

## Layers and boundaries (eslint-plugin-boundaries)

`eslint.config.mjs` declares four element types — `shared` (`src/shared`), `app` (`src/app`),
`routes` (`src/routes`) and `feature` (`src/features/*`, capturing the feature name) — and
`boundaries/dependencies` runs with `default: 'disallow'`. The allowed edges are exactly:

| From | May import |
|---|---|
| `shared` | `shared` only |
| `app` | `shared`, `app`, any `feature` |
| `routes` | `shared`, `app`, `routes`, any `feature` |
| `feature` | `shared`, `app`, and **the same feature** |

Consequences, each one a lint error (`Import cruza fronteira proibida (frontend-architecture skill)`):

1. **A feature never imports another feature.** If two features need the same thing, it goes down to
   `shared/` (generic) or up to `app/` (shell-level composition, e.g. `app/plan`, `app/copilot`).
2. **`shared` never imports `features` or `app`.** `shared/ui` knows nothing about the domain — there
   is no `<ChargeCard>` there. If it knows what a charge is, it belongs to a feature.
3. **`app` may compose features** (the setup wizard, the copilot dock, plan banners) but holds no
   business rules of its own beyond that composition.
4. `test/` is outside `src/` and outside the boundary check; fixtures may import feature types.

Related rule enforced by `no-restricted-imports`: **only `features/*/api/`, `app/providers/` and
`shared/lib/api/` may import `@/shared/lib/api/client`** (see the `data-fetching` skill). Components
and pages call hooks.

## Routing (TanStack Router, file-based)

- Route files live in `src/routes/`; the Vite plugin (`tanstackRouter({ target: 'react',
  autoCodeSplitting: true })` in `vite.config.ts`) regenerates `src/routeTree.gen.ts`. Don't edit it.
- Naming: dots are path separators and `$param` is a param — `billing.$settlementId.tsx` →
  `/billing/$settlementId`. A trailing underscore on a segment (`login_.verify.tsx`) opts the child
  out of the parent's layout. `_authenticated.tsx` is a pathless layout route; its children live in
  `src/routes/_authenticated/`.
- **Routes stay thin.** A route file is `createFileRoute(path)({ validateSearch?, beforeLoad?,
  component })` and nothing else:

```typescript
export const Route = createFileRoute('/_authenticated/billing/$settlementId')({
    component: SettlementDetailPage
});
```

- **Guards live in `beforeLoad`, never inside pages.** `_authenticated.tsx` checks
  `context.session.isAuthenticated` and redirects to `/login` with `search: { redirect:
  location.href }` (to `/admin/login` when `VITE_APP_TARGET` is `admin`). `login.tsx` does the
  inverse. The session reaches the router through `createRootRouteWithContext<{ session }>()`
  (`__root.tsx`) and `<RouterProvider context={{ session }} />` (`main.tsx`).
- **Search params are validated in the route**: `validateSearch: z.object({ redirect:
  z.string().optional() })` (`login.tsx`) or a function returning a typed object (`activity.tsx`).
  Consume them with the typed hooks (`Route.useSearch()`, `useSearch({ from: '/login' })`,
  `useParams`), never by parsing `window.location`.
- Navigation state that must not live in the URL (challenge/setup tokens between login steps) goes in
  router history state; the allowed keys are declared once in `main.tsx` (`interface HistoryState`).
- `main.tsx` registers the router type (`declare module '@tanstack/react-router' { interface Register
  { router: typeof router } }`) — that is what makes every `to:` and `Link` path-checked.

### Admin vs tenant build

`VITE_APP_TARGET` (`unified` | `tenant` | `admin`, `src/shared/config/app-target.ts`) selects the
bundle. `npm run dev:admin` runs the admin target; for the `tenant` target `routeFileIgnorePattern:
'admin'` removes every `admin*` route file from the tree. Admin routes are `admin.*.tsx` /
`_authenticated/admin.*.tsx`, backed by `features/admin`.

## State ownership

| Kind of state | Where it lives |
|---|---|
| Server data (anything the API owns) | TanStack Query — never mirrored into `useState` |
| Filters/ids that define *which screen this is* | route params / validated search params |
| Form state | React Hook Form |
| Session (user) | `SessionProvider` (`useSession()`); the access token lives in `tokenStore` |
| Theme | `ThemeProvider` (`.dark` class on `<html>`, preference in `localStorage` key `revtriever.theme`) |
| Ephemeral UI (modal open, hover, a local page counter) | `useState` in the component |
| Live updates | `useRealtimeEvent` (socket.io) that invalidates the relevant query |

There is no global store library. Don't add one preemptively; a second real case comes first.
Copying server data into `useState` is a bug: it duplicates the source of truth and goes stale.

## Auth

- The access token lives **in memory** (`src/shared/lib/api/token-store.ts`), never in
  `localStorage`/`sessionStorage`. The refresh token is an httpOnly cookie set by the API.
- `SessionProvider` calls `restoreSession()` on boot (refresh, then `GET /auth/me`) and renders
  `SessionSplash` until `isRestoring` is false. When the token store is cleared the user is cleared.
- The client middleware renews on a 401 and retries once (see `data-fetching`). Pages never handle 401.
- Login has three outcomes (`authenticated`, `totp_required`, `totp_enrollment_required`, see
  `LOGIN_STATUSES` in `features/auth/types.ts`); the outcome drives navigation to `/login/verify` or
  `/login/setup`. Never treat 2FA as an error.

## Component size: how to stay under `max-lines-per-function: 40`

The limit is **40 lines per function in every repo, frontend included** (blank lines are skipped;
see the `conventions` skill). A component is a function, and so is a `describe` callback. JSX
counts, which is the point: it forces a screen to be composed, not poured into one function.

- **A page composes; it does not contain markup for every concern.** When a page grows, extract
  subcomponents into the feature's `components/` (one component per file, named export, kebab-case
  file name: `settlement-card.tsx` exports `SettlementCard`).
- **Extract hooks for logic.** State, handlers and derived values that serve one concern go to a
  `use-x.ts` hook next to the component (`use-wizard.ts`, `use-setup-alerts.ts`).
- **Extract pure functions** for decisions (`secondFactorStep(outcome)` in `login-page.tsx`) and
  move lookup tables to module-level `as const` maps. Small `if` chains beat nested ternaries in JSX.
- Early returns for loading/error/empty come before the main JSX; each state can be its own small
  component.
- Props get an explicit `interface` above the component (`readonly` fields); no inline giant types.
- Never "fix" the limit by squeezing statements onto one line or by adding a disable comment — split
  the function.

## Other conventions that the code follows

- Named exports only, no barrel files: import from the concrete file (`@/shared/ui/button`).
  ESLint forbids TS `enum` (`no-restricted-syntax`); use an `as const` map + union.
- Domain values (statuses, providers, environments) are constants derived from the generated API
  types or a local `as const`, e.g. `LOGIN_STATUSES`, `OVERAGE_POLICIES`
  (`... as const satisfies Record<OveragePolicy, OveragePolicy>`) — not quoted strings scattered over
  components.
- File names are kebab-case with a role suffix (`*.query.ts`, `*.mutation.ts`, `*.schema.ts`,
  `*-keys.ts`, `*.types.ts`, `use-*.ts`, `*.spec.ts(x)`); components are `kebab-case.tsx` too.
- `useEffect` is a last resort: derived state is computed, server state is Query's, events are
  handlers. An effect that syncs state is usually a bug.
- The typedef exemptions that exist because of this layout (`routes/**/*.tsx`, `main.tsx`,
  `features/*/api/*-keys.ts`, `*.schema.ts`, `types.ts`, `shared/config/*.ts`) are explained in the
  `conventions` skill.
